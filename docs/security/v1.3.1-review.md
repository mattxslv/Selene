**Selene v1.3.1: Defender detection and security review — 2026-10-28**

This records the original read-only investigation. The current security branch retires the elevated helper; see [migration and validation](windows-validation.md) for the fixes and remaining Windows work.

**Assessment:** A Defender false positive is plausible, but unconfirmed. The elevated helper combines several behaviors commonly associated with malicious software, while also exposing genuine local security weaknesses. No evidence of a Trojan payload was found in the reviewed helper. This is not a clean bill of health for the entire application or a reproduction of Defender's verdict.

**Scope and evidence**

Reviewed tag `v1.3.1`, commit `d57f09db047c7b9522259feae0f72de6c64a1f74`, rather than the outdated local main branch. The original temporary evidence directory contained source copies under `source/`; file links below refer to the immutable reviewed commit. No repository code, branch, antivirus settings, or Windows protections were changed. Release programs were not executed. Tools and downloaded artifacts were kept in `/tmp/selene-v1.3.1-audit/`.

Downloaded both actual assets from the [official release](https://github.com/mattxslv/Selene/releases/tag/v1.3.1). Both hashes match the digests returned by GitHub's release API. This establishes correspondence to the current published assets, not that they are harmless or reproducibly built from the tag. GitHub marks the release as non-immutable.

**Confirmed code findings; exploitability conditions stated separately**

1. **High: an unauthenticated file is an elevated command channel.** [SeleneHelper.cs:130–185](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/helper/SeleneHelper.cs#L130) reads `%LOCALAPPDATA%\\Selene\\elevated.txt` and accepts arbitrary numeric PIDs/HWNDs for close, freeze, thaw, and focus. There is no sender authentication, session/owner verification, game allowlist, PID creation-time validation, or check that an HWND belongs to the supplied PID. A same-user process with normal access to this profile directory can supply requests. While the helper is resident it polls them; starting an idle helper additionally depends on task run permissions. Operations remain bounded by Windows process protections: this does not establish the ability to terminate Defender/PPL processes, run arbitrary shell commands, or become SYSTEM. **Fix:** replace the file with authenticated, bounded local IPC and enforce authorization inside the elevated component. Restrict operations to explicitly authorized game process instances and Playnite windows; validate user/session, process creation time, image identity and window ownership. A pipe ACL limited to the same user alone does not distinguish Selene from other programs running as that user.

2. **High, conditional exploitation: elevated executable paths are not protected by this implementation.** [LocalGames.cs:330–332](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/LocalGames.cs#L330) locates the helper beside the add-on DLL; [lines 389–420](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/LocalGames.cs#L389) registers helper and game executables without checking or hardening their filesystem ACLs. If their executable or containing directory is writable by a non-elevated process, replacement can turn a subsequent elevated task launch into attacker code execution. Writable game directories and writable DLL search locations also require review. **Not tested:** actual Windows installation ACLs, DLL search behavior or a replacement exploit. **Fix:** put the privileged helper and dependencies in an administrator-managed location, protect parent directories and update operations, and verify signed publisher identity. Avoid permanent elevated game tasks targeting user-writable games.

3. **High, conditional exploitation: task registration trusts mutable temporary XML.** [LocalGames.cs:398–439](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/LocalGames.cs#L398) writes predictable `%TEMP%` XML names before requesting elevation. [SeleneHelper.cs:49–65](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/helper/SeleneHelper.cs#L49) then registers the XML through `schtasks /create ... /f` without checking its actions, principal or name. Another process able to modify those files can change task contents between writing and privileged consumption, including during the consent interval. It still requires the user to approve the elevation and the relevant write access; no Windows exploit was run. **Fix:** construct narrowly constrained task definitions inside a trusted elevated installer using Task Scheduler APIs. Validate structured input there; do not elevate arbitrary task XML from a writable temporary path. Random filenames alone do not solve the trust problem.

4. **Medium: suspension recovery is not guaranteed.** [SeleneHelper.cs:74–127](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/helper/SeleneHelper.cs#L74) records only PID/HWND, permits repeated suspensions of the same PID, and deletes its record even when resume fails. The outer exception handler exits without a finally-based thaw. It detects Playnite by process name alone, not its initiating process instance/session. Any nonempty request batch resets the inactivity timer. PID reuse can redirect later resume operations, and exceptions/helper termination can strand a game. **Fix:** make freeze idempotent, retain handles to verified process instances, preserve state until successful recovery, add bounded retries and explicit acknowledgements, and use an independent recovery mechanism. Finally cleanup helps ordinary errors but cannot recover from forced termination by itself. Prefer game-supported pause where available.

5. **Medium: queue races, replay and unbounded input.** [HomeNav.cs:5416–5428](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/HomeNav.cs#L5416) appends while the helper separately reads and deletes the file. An append between read and delete can be lost. A failed delete can leave already-read requests available for repeat processing. There are no request IDs, acknowledgements, size/count limits, deadlines or exclusive queue ownership. The client returns true immediately without verifying `schtasks` success. **Fix:** framed IPC with bounded messages, unique IDs, responses, expiry and explicit failure handling. Check the task process result rather than treating launch as acceptance.

6. **Medium: task naming, trust and lifecycle are weak.** [LocalGames.cs:303–308, 365–375, 396–397](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/LocalGames.cs#L303) checks existence rather than validating the registered action/principal/security descriptor. Tasks use highest available rights, demand start, unlimited execution time and IgnoreNew; the helper is hidden. Game tasks use sanitized display names and can collide with each other or the reserved `Selene\\Helper` name; `/f` overwrites existing tasks. No matching task removal was found in the reviewed registration/helper code. Tasks have no automatic logon/boot trigger in the generated XML, and are not explicitly SYSTEM tasks. Their actual account and DACL require Windows inspection. **Fix:** reserve the helper namespace, use stable game IDs, validate ownership and full task configuration before reuse, specify a deliberate principal/DACL, and implement uninstall/update cleanup. Keep elevation an explicit informed choice, not an automatic persistent entitlement based solely on detecting an elevated game.

7. **Medium: terminating all processes under a game folder can affect unrelated software.** [HomeNav.cs:5353–5395](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/HomeNav.cs#L5353) combines the game window PID with [LocalGames.cs:566–580](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/SeleneCore/src/LocalGames.cs#L566)'s folder-wide process list, and force-kills after four seconds. The helper likewise attempts a graceful close then kills after four seconds. Incorrect/shared folders, stale PIDs and unsaved game state can cause collateral loss. **Fix:** track the exact launched game and authorized children with process-instance handles, give an appropriate grace period and require a clear force-close action.

8. **Build/release integrity gaps, not proof of a compromised release.** [build.ps1:11–24](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/tools/build.ps1#L11) directly compiles a windowless optimized AnyCPU helper with the local Framework compiler, SDK and WPF dependencies. There is no signing step or explicit helper version metadata; the binary declares assembly version 0.0.0.0. The stage directory is reused, not cleaned. [package.ps1:14–38](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/tools/package.ps1#L14) invokes Toolbox without explicit native exit-code checks and checks required entries but does not reject unexpected files. This can package stale/unexpected stage contents. [release.py](https://github.com/mattxslv/Selene/blob/d57f09db047c7b9522259feae0f72de6c64a1f74/tools/release.py) updates versions/manifests; documented publishing is manual. No release workflow is present at this tag. **Fix:** clean isolated release builds, pin/verify build inputs, check every native exit code, enforce an exact package inventory, add real version/publisher metadata, Authenticode-sign and timestamp privileged binaries, and publish checksums plus build provenance. The inspected add-on did not contain unexpected extra binaries.

**Likely false-positive triggers — hypotheses, not Defender attribution**

The strongest candidate is the combination of a small unsigned windowless EXE, hidden highest-privilege scheduled-task registration, on-demand elevated execution without subsequent prompts, native process suspension/resumption, process termination, input synthesis and a persistent command-file loop. Those capabilities have legitimate game-management purposes here, but overlap with malware behavior. `SendInput`/Alt and `AttachThreadInput` are used for foreground-window control, not evidence of keylogging. `OpenProcess` requests suspend/resume access, not code injection. No network downloader, credential collection, remote-thread injection or antivirus-disabling logic was found in the reviewed helper.

A rebuild generating a new hash and the unsigned publisher state may also affect reputation. The helper's unchanged decompilation across 1.3.0/1.3.1 supports investigating that possibility. There is no evidence that `/optimize+`, AnyCPU or the ZIP extension alone caused the alert. No packer/obfuscator appears in the inspected build path and the helper decompiles normally. The main DLL does perform legitimate network/download operations, so the helper-only finding must not be generalized into a claim that all Selene is network-free.

**Antivirus testing and limits**

ClamAV 1.5.4 was downloaded from the configured distribution mirror and unpacked locally, without installing a service or changing system configuration. Freshclam successfully verified and loaded main database 63, daily 28166 and bytecode 339. Certificates were pointed at the package's own certificate directory; verification was not disabled. See the original `freshclam.log` and the preserved `v1.3.1-clamav.log` for evidence. The completed rerun reported OK for SeleneHelper.exe, SeleneCore.dll and SeleneCore.pext. The theme hit `Heuristics.Limits.Exceeded.MaxScanTime` after the default per-file scan time limit; it did not complete and must not be called clean. Because `--alert-exceeds-max=yes` was enabled, ClamAV counted this resource-limit alert in its 'Infected files: 1' summary. This is a scan-limit result, not a Trojan-family identification. The run used 3,628,193 known signatures, 200 MB maximum file size and 500 MB maximum scan size, and took 132.146 seconds. A preliminary run was interrupted during the theme scan; the completed rerun is in v1.3.1-clamav.log. No files were removed or quarantined by these scans.

This is a Linux machine without Windows Defender. There was no Windows sandbox execution, task ACL export, Defender Protection History, original flagged sample, detection family/name, engine/intelligence version or Microsoft verdict available. GitHub issue searches for Trojan, Defender and virus returned no matching issues; that does not disprove reports elsewhere or guarantee search completeness. No samples were uploaded to Microsoft or VirusTotal. A clean ClamAV scan cannot establish that Defender is wrong or that all code is safe.

**Recommended next steps**

Prioritize fixing the elevated trust boundaries (findings 1–3), then reliable process recovery/authorization and task lifecycle, then release integrity/signing. Signing may improve identification but does not repair security bugs or guarantee no detection. Obtain the original Defender event with exact affected path, SHA-256, detection name, engine and intelligence versions, action and whether detection occurred on download/extraction or execution. Compare that hash to this report before making any false-positive claim. Scan the same artifacts on a fully updated isolated Windows environment with Defender enabled, including archive extraction, task setup and normal game controls. Export task XML/DACLs and executable-directory ACLs. Submit the exact flagged artifact as a software developer through Microsoft's [submission process](https://learn.microsoft.com/en-us/unified-secops/submission-guide), with hashes, source references and behavior explanation. Microsoft recommends [consistent trusted signing and developer submission](https://learn.microsoft.com/en-us/defender-xdr/developer-faq); neither is a preapproval guarantee. Do not recommend exclusions or disabling protection to users.
